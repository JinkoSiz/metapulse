# MetaPulse

Сервис-агрегатор игр с Metacritic с LLM-резюме отзывов, веб-витриной и live-мониторингом.
Тестовое задание на позицию AI Automation Engineer.

Раз в час сервис берёт 20 игр, которые сегодня ещё не обрабатывал, складывает их в свою базу
(или обновляет уже существующие), вытягивает отзывы критиков и пользователей, делает по ним
два отдельных резюме через LLM, считает эмбеддинги для подбора похожих игр и ищет самый
популярный летсплей на YouTube, чтобы сделать заключение по рассказу блогера.

## Как это устроено

```
                     ┌──────────┐
   браузер ────────► │  caddy   │  автоматический HTTPS
                     └────┬─────┘
                          │
                     ┌────▼─────────────────────┐
                     │ web (FastAPI + HTMX)     │  список, карточка, /monitor, SSE
                     └────┬──────────────┬──────┘
                          │              │ enqueue / subscribe
                 ┌────────▼───────┐  ┌───▼─────────┐
                 │ PostgreSQL 16  │  │   Redis     │  очередь arq, pub/sub, lock, heartbeat
                 │ + pgvector     │  └───▲─────────┘
                 └────────▲───────┘      │
                          │              │
                     ┌────┴──────────────┴──────┐
                     │ worker (arq, cron @hourly)│
                     └───┬───────┬───────┬───────┘
                         │       │       │
          backend.metacritic.com │       └─► Anthropic (резюме) + Voyage (эмбеддинги)
                                 └─────────► YouTube Data API + транскрипты
```

Каждое обращение к нейросети — включая эмбеддинги и ошибки — пишется одной строкой в
`logs/llm/YYYY-MM-DD.jsonl`. Это не побочный лог, а архитектурное ограничение: `app/llm/client.py` —
единственное место в проекте, откуда вызываются Anthropic и Voyage.

Подробные контракты модулей: [docs/CONTRACTS.md](docs/CONTRACTS.md).

## Данные Metacritic

Сайт с 2023 года — Nuxt 3 SSR, и всё его содержимое отдаёт публичный JSON API
`backend.metacritic.com`. Проверено живыми запросами: ключ не обязателен, challenge Cloudflare
не выдаётся, ответы кэшируются на edge. Поэтому **HTML не парсится и headless-браузер не нужен** —
сервис ходит в тот же API, что и сам сайт.

| Что | Эндпоинт |
|---|---|
| New Releases (первый заход дня) | `finder/metacritic/web?componentName=new-releases-carousel&sortBy=-releaseDate&limit=20&mcoTypeId=13` |
| Browse «Новые» (последующие заходы) | `finder/metacritic/web?sortBy=-releaseDate&productType=games&offset={n}&limit=50` |
| Детали игры | `games/metacritic/{slug}/web` |
| Userscore платформы | `reviews/metacritic/user/games/{slug}/platform/{platform}/stats/web` |
| Отзывы | `reviews/metacritic/{critic\|user}/games/{slug}/web?offset={n}` |

Три особенности, найденные замерами и зашитые в клиент:

1. Эндпоинт отзывов критиков **игнорирует `limit`** и всегда отдаёт 10 элементов — нужна
   пагинация по `offset`. Пользовательские отзывы `limit` уважают (проверено до 200).
2. Userscore платформы берётся **только path-сегментом** `/platform/{slug}/stats/web`.
   Query-параметр платформы молча игнорируется и вернёт цифры lead-платформы — тихая порча
   данных, поэтому на это есть отдельный тест.
3. `finder`-элементы не содержат списка платформ, а `userScore` в них почти всегда `null` —
   и то, и другое добирается из деталки и stats-эндпоинта.

Лестница деградации на случай, если Cloudflare ужесточит посадку, переключается конфигом:
JSON API → тот же запрос через резидентный прокси (`MC_PROXY`) → парсинг SSR-HTML.

## Выборка «каждый день заново»

Требование задания — каждый новый день начинать выбор сначала: сперва New Releases, потом
страницы browse — закодировано схемой, а не расписанием:

* `crawl_state` ключуется датой. Нет строки на сегодня → она создаётся с `phase='carousel'`,
  `next_offset=0`. Наступление нового дня само по себе означает «начинаем заново».
* `daily_seen(day, mc_id)` — журнал «сегодня уже обработал». Кандидаты из листинга проходят
  анти-join по нему, поэтому один и тот же тайтл не берётся дважды за день, даже если выдача
  переупорядочилась между страницами (у игр одной даты релиза это бывает).
* Запись в `daily_seen` делается **после** успешной обработки игры: падение посреди прогона не
  «съедает» игру, следующий заход возьмёт её снова.

## LLM-контур

* **Резюме отзывов** — две отдельные генерации на игру (критики и пользователи), модель
  `claude-haiku-4-5` со structured outputs (`likes[]`, `dislikes[]`, `tl_dr`), ответ на русском.
* **Обновление при повторных обходах** — по `input_hash`: sha256 корпуса отзывов. Если корпус
  не изменился, LLM не вызывается вовсе; если изменился — резюме перегенерируется, и это видно
  по `summaries.updated_at`. Стоимость одной игры ~$0.02–0.035, а повторные обходы почти бесплатны.
* **Похожие игры** — эмбеддинг `title + жанры + описание` через `voyage-4-lite`, хранение в
  `vector(1024)`, точный косинусный поиск (`ORDER BY embedding <=> :vec`). ANN-индекс осознанно
  не создаётся: при сотнях игр он не нужен. Без ключа Voyage работает лексический фолбэк по
  жанрам и `pg_trgm`, так что похожие игры есть даже на голой установке.

## Веб-интерфейс

| Страница | Что умеет |
|---|---|
| `/` | список игр, поиск по названию, фильтр по платформам, сортировка по рейтингу |
| `/game/{slug}` | обложка, описание, разработчик, таблица платформ с Metascore и Userscore, трейлер, оба резюме, летсплей, похожие игры (кликабельны) |
| `/monitor` | live-мониторинг: статусы воркеров, счётчики, лента событий, история прогонов, кнопка принудительного запуска |
| `/llm-logs` | выгрузка JSONL-логов переписки с нейросетью |

Мониторинг — SSE (`/api/events`): воркер публикует события в Redis pub/sub, веб транслирует их
браузеру. События дублируются в `task_events`, поэтому лента переживает перезапуск.
Кнопка запуска ставит ту же задачу, что и cron, и защищена тем же Redis-локом — двух
одновременных прогонов не бывает.

## Запуск

### Локально (Docker)

```bash
cp .env.example .env          # ключи API можно оставить пустыми — см. «Работа без ключей»
docker compose up -d --build
```

Веб — http://localhost:8000 (через Caddy — http://localhost). Миграции применяются автоматически
при старте контейнера `web`.

### Локально (без Docker, только приложение)

```bash
docker compose up -d postgres redis     # инфраструктура
uv venv --python 3.12 && uv pip install -e ".[dev]"
.venv/bin/alembic upgrade head
.venv/bin/uvicorn app.web.main:app --reload      # веб
.venv/bin/arq app.pipeline.worker.WorkerSettings # воркер
```

### Тесты

```bash
.venv/bin/pytest -q
```

Тесты парсеров и выбора летсплея работают без сети; тесты дневной выборки используют локальный
Postgres из compose.

## Ключи API

| Переменная | Нужна для | Если не задана |
|---|---|---|
| `ANTHROPIC_API_KEY` | резюме отзывов, заключение по летсплею | игры собираются и показываются, блоки резюме пустые |
| `VOYAGE_API_KEY` | эмбеддинги для похожих игр | работает лексический фолбэк (жанры + похожесть названий) |
| `YOUTUBE_API_KEY` | поиск летсплея | блок летсплея не показывается |
| `YOUTUBE_PROXY` | транскрипты с сервера | на датацентровом IP YouTube блокирует запросы — транскрипт не получить |
| `MC_PROXY` | обход Cloudflare, если посадка ужесточится | не требуется при текущем поведении Metacritic |

**Работа без ключей.** Сервис спроектирован так, чтобы деградировать, а не падать: сбор игр,
платформ, оценок, отзывов, веб-витрина, поиск, фильтры и мониторинг работают полностью без
единого ключа. Ключи включают LLM-резюме, семантические «похожие игры» и летсплеи.

**`YOUTUBE_PROXY` — не опция, а требование для доп. части 1 на сервере.** YouTube блокирует
транскрипты с датацентровых IP в течение нескольких запросов. Резидентный прокси (например
Webshare) стоит ~$3.5 разово, порядка $0.003 за видео.

## Почему очередь, а не планировщик в процессе

Для 20 игр в час хватило бы `APScheduler` внутри веб-процесса, и это был бы честный выбор.
Очередь взята за три конкретных свойства, а не «чтобы было по-взрослому»:

* задача переживает перезапуск контейнера и ретраится, а не теряется посреди прогона;
* один и тот же код исполняется и по расписанию, и по кнопке из интерфейса — с общим локом,
  поэтому ручной запуск не может задвоить обработку и сломать дневной учёт;
* мониторинг реального времени получает события из воркера бесплатно, не деля event loop с
  веб-слоем: тяжёлый прогон не подтормаживает интерфейс.

Цена решения — Redis как дополнительная зависимость. На одном VPS это приемлемо.
